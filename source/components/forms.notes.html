Every input control in the dark rebrand, each in its five states, on one phone-width sheet. This is the kit the sign-in, onboarding, club-selection, create-idea and account screens are all built from, so a decision made here propagates everywhere.

What you're looking at

Ten controls, five states, one set of rules

A form kit is not a screen — nobody ever sees this page. It exists so that the twenty screens that do contain a field all contain the same field, and so that the four inconsistencies the current app carries into every form are fixed once rather than twenty times.

Because it is a kit and not a flow, it stays on one device. Everything here is a specimen of a control — including the compound phone field, which appears five times because it has five states, not because there are five screens. A member never navigates between any two things on this page.

Two of those fixes were choices rather than corrections, and they are the substance of this page. The app ships four different field-label conventions across eight screens; one had to win. It also renders the primary button at six different heights, from 62 to 96 pt; one number had to win there too. The reasoning for both is set out in the decisions below, because they are the kind of choice that is cheap now and expensive after twenty screens are built on it.

Ten controls are shown — text, password, textarea, select, date, phone, search, toggle, checkbox, radio — each in default, focus, filled, error and disabled. Then the grouped radio list, the two-up field row, the three validation rows and the form footer. The focus specimens are static so the whole sheet reads without a live caret, but they render exactly what :focus-within produces; the password toggles, the textarea counter and the search clear are all live.

Provenance

What is reused and what is new

This is a system kit and it is almost entirely proposed. No form control is designed in the new brand. What comes from the existing product is the inventory — which controls exist, what they are labelled, what they validate, which screens pair which fields — taken from the sign-in, recovery, profile, create-idea and club-selection screens. The appearance of every one of them is new, and in five places the existing behaviour is deliberately overruled.

Reused from the Figma file

  • Control inventory — text, password, textarea, select, date, compound phone, search, toggle, checkbox and radio, and the label wording on each
  • The 52 px action — lifted from the Like pill already shipping on the idea card, which is where the one height comes from
  • Surfaces, radii and hairlines — #1C2129, R12, R pill and the two line values, all sampled
  • Section container — the bordered #080A0C wrapper, reused for the form footer
  • Row pattern — the hairline-divided row, reused for switch rows and grouped radios
  • Badge tile — the monochrome code chip from the Merits club chip, reused as the ISO country tile
  • Accent-wash ring — the same translucent accent already used for active rows, reused as the focus ring

New in this proposal

  • One label convention — outside, above, 12.5/600 white, replacing the four the app ships: inside the box above the value, absent entirely, outside in muted lilac, and outside in semibold white
  • One control height — 52 px for every single-line control and every button, replacing six primary-button heights between 62 and 96 pt
  • One focus treatment — accent border and wash ring, on every control type including the toggle and the checkbox
  • One error treatment — red border, red ring, red glyph and a written message, on every control
  • Toggle inversion fixed — accent moved from the knob to the track
  • Phone divider — the missing boundary between the dial-code zone and the number
  • ISO tile instead of emoji flags — the current field renders country flags from the platform emoji font: full colour, different on every OS version, meaningless to a screen reader, and the only thing on the screen outside the palette
  • Two-up alignment — subgrid plus a fixed control box, against a pairing that currently drifts about 3 pt at the label and 6 px in height
  • Date format hint — DD/MM/YYYY as the placeholder
  • Textarea counter — live, at 250 characters
  • Search clear affordance
  • Required marker — an accent asterisk; nothing currently marks required fields
  • Accessibility wiring — aria-invalid, aria-describedby, aria-pressed, aria-checked and real hidden inputs throughout

Decisions

What we need from you

  1. Is outside-above the right label convention?

    The app ships four conventions across eight screens, so this kit had to pick one, and it picked outside the box, above the control, 12.5/600 white. It is the only one of the four that works for every control here: a switch row, a checkbox row and a compound phone field have nowhere to put an inside label, and an absent label leaves a placeholder doing a label's job — which disappears the moment someone types. It also keeps the box a single-purpose value container, which is what lets every control hold one fixed height. Confirm it, because changing it later means touching every form in the product.

  2. Is 52 px the right control height?

    Six heights currently ship for the same primary button, from 62 to 96 pt. 52 px is the one already in use on the idea card's action, it clears the 44 px tap minimum comfortably, and eight fields plus a footer still fit an 812 pt screen at that size — which the 96 pt version does not. The trade is that the primary action is now no taller than the fields above it, so emphasis comes from the accent fill rather than from size.

  3. Which fields are actually required?

    Four fields carry the accent asterisk here, on our reading of what registration needs. Nothing in the current app marks required fields at all, so the list is assumed — and the answer determines when the footer's primary can enable, which is the difference between a form that guides and a form that rejects.

  4. Date order, and whose locale?

    The placeholder commits to DD/MM/YYYY. The value in the export, 02/06/2001, is ambiguous, and the app is being built for clubs in at least three countries. Either the format follows the device locale — in which case the placeholder must too — or it is fixed, in which case the hint stays and everyone reads the same thing.

  5. Are two-character country codes acceptable in place of flags?

    The ISO tile is deterministic, monochrome, screen-readable and free of raster assets, and it keeps the phone field inside the palette. The cost is that AU is less instantly recognisable than a flag to someone scanning a list of thirty countries. If flags are wanted, they need to be a commissioned monochrome set, not the emoji font.

  6. Is 250 characters right for an idea?

    The textarea counter enforces 250, which is about three lines of argument. The comments composer proposes 600 for a reply. If those two numbers should relate to each other — or if either is set by a database column — we would rather match the real limit than pick a plausible one.
