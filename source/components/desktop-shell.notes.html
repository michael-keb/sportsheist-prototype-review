Not a phone screen. This is the desktop web shell — a fixed left navigation rail beside the War Room, with the phone's horizontal card rails re-laid as multi-column grids. It renders here in a full-width stage rather than a device frame, because that is the shape it is designed for; the phone build takes over below 900px.

What you're looking at

One product, two ways of navigating

On the phone, the five destinations live in a floating pill at the bottom of the screen: only the destination you are on shows its name, the other four are outline glyphs. That works because a thumb is at the bottom of the device and there is no room for five labels. On desktop the same five destinations move to a left rail where every label is visible all the time, because there is width to spare and a mouse has no reach problem.

The two are the same navigation, not two designs. Same five destinations in the same order, the same five glyphs at the same 1.7 stroke weight, and the same rule for the selected one: it becomes an acid-green pill with dark ink and it is the only row that carries both a glyph and a word. On the phone that pill hugs the icon and label; in the rail it spans the full row and picks up a trailing chevron. Nothing else about the app changes — the hero, the section headers, the cards and every control inside them are the components already built for mobile, at their measured sizes.

The page shows three states stacked so they can be read together: the rail expanded, the rail collapsed to icons, and a proposal opened in a right-hand detail panel. Resizing the browser window drives the real behaviour as well — the rail collapses on its own at 1180px and hands over to the bottom pill at 900px.

States

What varies, and at what width

Two rules run independently, because they answer different questions. How many columns is a question about the space the cards actually have, so it is measured against the content region. Which navigation is on screen is a question about the window, so it is measured against the viewport. Keeping them apart is what lets the detail panel open, or the rail collapse, without the cards distorting.

Provenance

What is reused and what is new

Unlike most of this library, a desktop layout was designed: the export set carries desktop frames, and they are where the left-rail navigation, the wide hero and the strapline that never appears on mobile all come from. So the shape of this screen is a reproduction. What is new is everything the static frames could not specify — the rail's exact geometry and its collapsed state, how many columns a grid takes at a given width, and what happens when the window is resized.

Reused from the Figma file

  • The desktop layout itself — left rail, wide hero and multi-column content are the designed desktop frames, reproduced rather than reinterpreted
  • Token block — copied verbatim from merits.html. No colour, radius or type value was added.
  • Hero banner — construction, 138px height, gradient, triangle opacities, acid peaks and knockout prop from war-room.html.
  • Section header — label, acid +, filter, View all ↗, and the lens-flare divider, from war-room.html.
  • Idea card — byline, clamped title, body, countdown, tag, sunken panel, 64px likes gauge and 52px CTA, from idea-card.html.
  • Voting card — approve meter, threshold tick, legend and votes-cast line, from war-room.html.
  • Ballot rows — the ranked option row with its 25px slot, from voting-card.html.
  • Card foot and quiet link — the card__foot + Details ↗ row already used by the Results card, reused as the panel-open affordance.
  • Five nav glyphs — the tab-bar icons from merits.html, at the same 1.7 stroke.
  • Log-out glyph — the door-and-arrow icon from profile.html.
  • Tab bar — the whole floating pill from merits.html, for widths under 900px.
  • Photography — the eight portraits and the knockout athlete from the Figma exports.

New in this proposal

  • Rail geometry — 230px on #1C2129. The left rail is in the designed desktop frames, but its exact width, row height and internal spacing are not specified there, so these values are our proposal.
  • Monogram — the hero's three-peak range motif in #0B0E06 on a 34px acid square. Reuses shipped geometry rather than drawing a new mark.
  • Wordmark — SPORTSHEIST set in the system stack at 13.5px / 800 / .05em. There is no drawn logotype in the exports.
  • Collapsed rail — 72px, icons only, plus the 44px square active tile.
  • Collapse control — lets a member pin the rail open or closed regardless of window width.
  • Card grids — the mobile carousels re-laid as fixed-count grids with a 16px gap, and equal-height rows with the numbers block bottom-aligned.
  • Content cap — 1240px, stepping down to 960 / 660 / 420px, so a wide monitor adds columns rather than inflating cards.
  • Container-driven columns — the grid reads the width of its own content region rather than the window, so the shell behaves correctly with the panel open, with the rail collapsed, and when it is embedded in a page narrower than the browser. A viewport fallback covers browsers without container queries.
  • Detail panel — 380px on #080A0C, with the sticky Not now / Vote here footer and the read-only Standing by option list.
  • Card "Open" flag — the acid ring and the Open pill that mark which card the panel belongs to.
  • Section header count — the 4 open / 4 live figure beside the label. Desktop shows the whole set at once, so the count earns its place; it does not exist on mobile.
  • Hero at width — the repeated field triangles and the fixed-pixel acid peaks, so the banner reads correctly at 1240px instead of being stretched.

Decisions

What we need from you

  1. Can we see the desktop frame from Figma?

    The brief describes it, but no desktop SVG sits alongside the mobile exports in components/_assets, so we could not measure it. Everything structural here is our reading of the description: rail width 230px, collapsed width 72px, nav row height 44px. If the frame exists we will re-measure against it.

  2. Is there a real monogram and logotype?

    We built the mark from the hero's own acid peaks and set the wordmark in the system font, because the exports contain no logo asset and hand-drawing one would have been worse. If a brand mark exists, it drops straight into the 34px slot.

  3. Should the hero grow taller on desktop?

    We held it at the measured 138px, so the desktop banner is the phone banner made wider. At 1240px that is a shallow band. Going to 180–200px would look more deliberate on a monitor, but it would be a new value and it would put desktop and mobile out of step. Our recommendation is to keep 138px until you tell us otherwise.

  4. Is 900px the right handover point?

    Below it we drop the rail and show the phone's bottom pill. That means a small laptop window or a landscape tablet gets phone navigation. The alternative is keeping the 72px icon rail all the way down and never showing the pill on the web. We chose the handover because it keeps one navigation visible at a time.

  5. Should Log out be red here?

    The mobile Profile screen treats it as destructive. In the rail we kept it #99A0AE going white on hover, because a permanent red row in the chrome reads as an error state, and #E2564A on #1C2129 is only 4.36:1 — large-text AA. The confirm sheet still carries the red.

  6. Does "open as a full page" exist?

    The panel head offers it beside the close button, on the assumption that a proposal has its own URL worth sharing. If proposals are panel-only, we remove that button.

  7. Results and Actions

    We built Ideas and Voting as grids, as briefed. Results and Actions use the same section header, the same divider and the same grid; only the card interior differs, and those interiors are already built in results-actions.html. Confirm they should land on the same War Room page rather than behind View all.
