The two recognition routes reached from Profile: the Hall of Fame roll of award winners, and the tabbed Achievements screen. Nine screens — six rebuilt from the capture set, three that have never been drawn at all.

Since this was written — 31 July 2026

Three of the defects below have been fixed in the app

These notes argue from the code as it stood when the screens were drawn. Some of that code has since changed, because these findings were acted on. The screens are still the right proposal — but do not read the following as outstanding faults.

  • Achievements is no longer reached through a commented-out push. The row was removed from profileRows in profile_body.dart instead, so the screen is deliberately absent rather than accidentally unreachable. The question of whether it ships is still open.
  • The leader-status band boundaries are fixed. The comparisons are now inclusive (>=), so exactly 0.95, 0.85 or 0.75 resolves to the right tier.

Everything else in this file was re-checked against the code on the same date and still holds.

What you're looking at

Two routes nobody can reach today

Both of these screens are in the design record and neither works in the shipped app. Profile → Hall of fame draws a chevron, implying it goes somewhere, and its tap handler is a bare break — profile_body.dart:375–376. Profile → Achievements has its navigation commented out, profile_body.dart:391–393, so the screen that does exist in the code is unreachable. There is no Hall of Fame anywhere in lib/: no page, no route, no widget, no model. This is the first build of it.

What the code does have is an achievement_screen.dart that looks nothing like the capture. It is a white screen (backgroundColor: CColor.white, line 34) with no tabs, no gold frame, no laurels and no empty state, whose list is itemCount: 4 repeating one hard-coded row — MOST VALUED FAN OF THE MATCH / Feb 16, 2024 — four times, with no cubit and no API call. The captured dark screens and the code are two different products.

Everything the captures put on screen is gold, and none of the golds is a brand colour. #D4AF37 (the plaque frame and roundel ring) and #B28401 (the laurels) do not appear anywhere in the codebase — we grepped. #DFAA11 (the award pill, the podium ring, the winning score, the crown) is real, and it is CColor.colorVeto: the amber the app paints a blocked proposal with. So today a celebration and a veto are the same colour. The new palette has no gold and no metallics, so rank here is carried by a numeral, ring opacity and scale — the podium construction already shipping on the Merits tab.

Nothing on this page is a new idiom. The Season dropdown and the Award sheet are the corrected Hall of Fame pair already specified in sheets.html. The announcement is dialogs.html's dialog shell. The empty panels, the "nothing to do yet" line and the loading bones are states.html's. The segmented control is filters-pickers.html's. The opponent crest sits on club-selection.html's plate.

Provenance

What is reused and what is new

Reused from the Figma file and the library

  • Token block — merits.html verbatim. Not one value invented.
  • Podium and plinth — the Merits-tab construction, re-pointed at award counts: grid, ring shadows, numeral plate, name and score.
  • Row, board, section container, status pill, tag, icon button, pill button, note card — all from merits.html / merit-detail.html.
  • Season dropdown and Award sheet — the corrected Hall of Fame pair, already specified and built as a specimen in sheets.html, including its three award names and their sub-copy.
  • Sheet shell and option row — sheets.html.
  • Dialog shell, icon tile, action row, scrim — dialogs.html.
  • Empty panel, "nothing to do yet" pill, peak illustration, skeleton bones — states.html.
  • Segmented control — filters-pickers.html's two-half .tax.
  • Club crest plate — club-selection.html, at the 28px dense size with the short-code fallback.
  • Award names — Member of the Match / Week / Season, the only place the award family is named in code (enum.dart:191–192).
  • The four leader tiers and their thresholds — read straight out of getLeaderShipStatus(), profile_body.dart:402–420, with the strings from en.json:83–89.
  • Blurred backdrop — the one thing worth keeping from HF-01 and HF-03.
  • Portraits — _assets/avatars.css.

New in this proposal

  • The Hall of Fame screen itself — nothing in lib/ renders one.
  • Rank without metal — a numeral plate plus ring opacity replaces the single gold ring, and there is no silver or bronze anywhere. The captures have no rank numerals at all.
  • The vacant slot — a dashed accent hairline labelled Vacant, instead of an empty grey circle labelled 0 points.
  • A heading between the podium and the list — ROLL OF HONOUR. The captures put ~57pt of bare canvas there with no heading, divider or label, and nothing on screen explains why the podium reads 908 points while the first list row reads 910.
  • Per-field labels — SEASON and AWARD, replacing one plural heading over a pair of unlabelled controls.
  • Dates that resolve — every date carries a weekday, and the season sits in the field directly above. No date anywhere in the capture set carries a year, on a surface whose primary filter is the season.
  • A dismiss control on the announcement — a ✕ and a Not now. The live modal draws no ✕, no "Later", no drag handle and no stated tap-out.
  • Loading — frame 5. No loading state is captured for any of these screens, and the shimmer the code already defines is never called.
  • Achievements populated — both tabs — frames 7 and 9. Nothing in the capture set shows either tab with data.
  • The tier ladder — the four influence tiers drawn as a ladder with the band each one sits in and the distance to the next. The names and thresholds are the code's; the ladder, the bar and the explanation are ours.
  • Empty-state copy that is not a lookup error — replacing No current season found for the default club.
  • One currency word — merits, matching merit-detail.html. The live product calls the same figure points, Reputation Points and credit transactions, and the API calls the award member_honored while the UI calls it Member of the Match.

Decisions

What we need from you

  1. Does the Hall of Fame survive as its own destination?

    merit-detail.html assumed one badge collection replaces the Achievements tabs and that Hall of Fame survives only as the Who holds it section on a badge. This component is built on the opposite assumption — Hall of Fame stays a separate route from Profile, and Achievements keeps its two tabs — because both are documented screens. The two builds cannot both ship as they stand. Rule on one of three: keep all three surfaces, fold Achievements into the badge collection and keep Hall of Fame, or fold everything into badges. This is the decision that changes the most.

  2. What is a playoff title, and is it even yours?

    Nothing defines this. The word playoff appears in the codebase only as an email-notification toggle — 'Game/Playoff Emails', enum.dart:193–194 — and there is no playoff model, list or endpoint. We built the most defensible reading: a title is the club's, shared with every member who was voting when it was decided, worth no merits and never lost. If a playoff title is instead something the member wins, frame 7 is wrong and the tab needs specifying from scratch.

  3. Is "Leader status" the influence ladder, or something else?

    The tab is captured as Leader status and the code's concept is spelled leader ship — getLeaderShipStatus() at profile_body.dart:402–420, returning MEMBER, EARLY INFLUENCER, EMERGING INFLUENCER, LEADING INFLUENCER from the ratio reputationPoint / totalPoint. We have assumed they are the same thing and built the tab as that ladder, which is the only way to fill it with real content. Two things follow. First, the label: "Leader status" does not say it is about influence, and the tier names are the more interesting words — we would rename the tab Influence. Second, a defect worth fixing before it ships: that function compares with < on both sides of every band, so a member sitting exactly on 0.95, 0.85 or 0.75 falls all the way through to MEMBER.

  4. What does the podium actually rank?

    The captured podium shows one holder at 908 points with two slots labelled 0 points, above a list whose first row reads 910 points, and nothing on screen relates the two. We have assumed the podium is the top three members by awards won in the selected season, and the roll beneath it is every individual award, newest first. That is what makes the vacant slot meaningful and the two figures agree. If the podium is instead the single current holder, it should not be a three-slot podium at all.

  5. What is an award worth, and is a season a split year?

    Placeholders: Member of the Match 250 merits, Week 400, Season 1,000. The live modal says 35 Reputation Points for Member of the Match, against podium scores in the 908–910 range, so the two numbers on the live screens are not on the same scale. Separately, we have rendered seasons as 2025/26, matching sheets.html. The captured dropdown reads Season 2025 and no date on any of these screens carries a year, so we cannot tell whether a season is a calendar year or a split year. Confirm the values, the word for the currency, and the season identifier.

  6. Should this announcement and the badge award be one moment?

    merit-detail.html frame 4 already announces Member of the Match as a badge earned. Frame 4 here announces the same event as an award with points, a prize and a Hall of Fame place. In the live app they are the same thing happening once. We have assumed one announcement, and this dialog is it — a dialog rather than a celebration screen, because it is presented over the list it leads to. If you want the fuller celebration, the badge moment in merit-detail.html is the one to keep and this frame comes out.

  7. Two bugs to confirm, not design questions.

    First, enum.dart:111 and enum.dart:117 are byte-identical, so ProfileSettingEnums.club resolves to the Hall of Fame label — both the Club row and the Hall of Fame row would read HALL OF FAME. (The enum is currently dead code, so nothing renders it, but the Profile menu is built from the same strings.) Second, both routes are unreachable: profile_body.dart:375–376 is a bare break and :391–393 is a commented-out pushNamed. Neither is a rebrand decision, but nothing on these nine screens can be tested until they are fixed.

  8. The default avatar is still a blocker.

    Repeating it because this feature is where it does the most damage. The current default avatar is watermarked marketing key-art: the circular crop cuts the burned-in wordmark to SPORTSHEI, and a red …WED BY 1.00 PIXELS watermark plus a yellow-and-black hazard bar are plainly legible at the 90pt podium size. The same image renders five times on one Hall of Fame screen. Every portrait here comes from _assets/avatars.css instead, but a licensed default-avatar asset is needed before any of this ships.
