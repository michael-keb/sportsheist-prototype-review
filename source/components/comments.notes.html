The discussion that hangs off a War Room proposal, and the composer that feeds it. This is where members argue a case before the ballot settles it — so it carries the debate half of the product, and it has to do that without ever looking like the vote itself.

What you're looking at

A debate surface, not a second ballot

Every proposal in the War Room gets a thread. Members make a case, answer each other, and signal whether they accept an argument — and then, separately, they vote. The whole design problem on this screen is keeping those two acts visibly apart. If agreeing with a comment looks like voting, members will think they have voted when they haven't, and the count will be wrong for reasons nobody can see.

We chose agree / disagree over a generic like. SportsHeist is about club decisions, so "I accept that argument" is the useful signal and "I enjoyed reading that" is not. Then we made it structurally impossible to mistake for the ballot: agreement is ink, never a fill. The ballot's signature is a filled accent pill, an accent-wash row with a 3 px accent bar, a percentage and a threshold bar. None of those four appear anywhere in the thread. The only accent fill on the entire screen is the 44 px send button, and that means post, not support. There is also a plain-English line under the sort bar saying agreeing does not change the ballot, because styling alone should not have to carry a claim that important.

The composer is a rebuild rather than a restyle. The live build ships a ~41 pt pill field with no growth, no counter and a grey send glyph that reads as permanently disabled. Ours starts at 44px, grows a line at a time to a 112px text cap, shows a character counter only when the member is within 80 characters of the limit, and puts the send button on a real tap target. Because it is pinned, it sits outside <main class="screen"> as the build contract requires.

Threading, agree/disagree, sorting and all three moderation states are new. The shipped model — MComment in lib/models/src/proposal/comment.dart — is flat: user, proposal, content, created_at, updated_at. No id, no parent, no reaction counts, no moderation flags. Every one of those fields has to be added for this screen to exist.

Provenance

What is reused and what is new

Reused from the system

  • Token block — copied verbatim from merits.html. No colour, radius or type value on this screen is new.
  • Row geometry — Merits' .board / .row: #1C2129 panel, 13px vertical padding, 1px rgba(255,255,255,.045) hairline, none on the first child.
  • Avatar — border-radius:50%, background-size:cover, background-position:center 22%. Portraits from _assets/avatars.css.
  • Crest tile — Merits' .crest / Forms' .iso monochrome badge, scaled to 34px for the club account and 16px for the CLUB / Moderated / Reported markers.
  • Accent ring on a portrait — Merits' first-place plinth device, reused to mark the viewer's own comment.
  • Field, focus ring and counter — Forms' .ctl / .ctl--area: 12px radius, 1px hairline, accent border plus 3px accent wash on focus, red border plus 3px red wash on error.
  • Buttons — Forms' .btn at 52px on the pill radius, secondary variant for the empty state.
  • Segmented control — .tax from results-actions.html, unchanged, for the three sort orders.
  • Icons — inline SVG, 24-box, round caps and joins, weight matched to size: 1.5 for the empty-state art, 1.7 for the official shield, 1.9 for the reply / eye-off / flag / send glyphs, 2.2 for the tick and cross, 2.4 for the overflow dots.

New in this proposal

  • Agree / disagree on a comment — no reaction of any kind exists in the build. Built as an ink-only 34px inline control so it can never be confused with the ballot. Needs agree_count, disagree_count and the viewer's own position on the model.
  • Threaded replies, one level — MComment has no id and no parent_id, so a reply cannot currently be attached to anything. Both fields are required.
  • Reply expander — a thread cap, so a 40-reply argument does not bury the next comment. Needs a reply count on the parent.
  • Club / official account marker — the build renders every author identically. Five non-colour distinguishers, and an is_official plus is_pinned flag to drive them.
  • Sorting — the build sorts newest-first with no control. Three orders, remembered per member.
  • Hidden by moderation, with a separate author view — no moderation exists in the build at all. Needs a moderation status, a reason code and a moderator note.
  • Deleted tombstone — needs a soft-delete flag rather than a row removal, so replies survive.
  • Flagged pending review, counts frozen — needs a report count and a review state, plus the report action itself behind the comment overflow.
  • Character limit and counter — the build has neither; content is an unbounded string. Assumed 600.
  • Growing composer with a 44 px send — the live control is a fixed pill with a tiny grey send button.
  • Ballot disclaimer line — a sentence, under the sort bar, doing in words what the styling does visually.
  • Proposal subject panel — the thread's subject, so a scrolled discussion still says what it is about.

Decisions

What we need from you

  1. Is a 44 px send button acceptable when the kit's icon button is 38 px?

    The system ships a 38px circular icon button for chrome — search, filter, close. 38px is below the 44 pt platform minimum tap target, which is tolerable for a button you press occasionally and wrong for the one control on the screen a member presses every time. Send is built at 44px. We would rather raise the kit's icon button to 44px everywhere than keep two circle sizes, but that is a system-wide change and it is your call.

  2. Is the comment limit 600 characters?

    content is an unbounded string in the build, so there is nothing to copy. We assumed 600 — long enough for a real argument with a statistic in it, short enough that a thread stays scannable — with the counter appearing at 80 remaining and hard input stopping at 700 so the over-limit state is reachable and recoverable rather than silently truncating.

  3. How many reports auto-hide a comment before a moderator sees it?

    The built default is: a reported comment stays readable, its counts freeze, and a moderator reviews it. For a club with members under 18 that may be too permissive. We propose auto-collapsing behind a one-tap reveal on the third independent report, with a moderator SLA of 24 hours. Both numbers need your sign-off, and they are a safeguarding decision rather than a design one.

  4. Who moderates, and can a club officer moderate its own critics?

    We have drawn the member-facing side of moderation, not the moderator's tools. The open question is governance: if a club officer can hide comments on the club's own proposals, the debate function is compromised. We assumed moderation sits with SportsHeist platform moderators, with club officers able to report but not hide. If clubs are to self-moderate, the hidden-comment notice must name who hid it.

  5. Is one level of nesting enough?

    At 375pt a second indent leaves roughly a 40-character measure, which is unreadable, so replies to a reply land flat in the same thread. That is the right call for phone width but it means a long back-and-forth loses its structure. If deeper argument threading matters, the alternative is a full-screen thread view pushed from the expander — more work, and worth deciding before build.

  6. Should disagreeing be visible to everyone, or only its total?

    As built, both counts are public and the member's own position is visible only to them. A club could reasonably want the disagree count hidden — it discourages dissent when a thread is one-sided — or shown only to the comment's author. We built the most transparent option: both counts public. Changing it is a copy and visibility change, not a redesign.

  7. Does a pinned club comment belong in the count?

    The header reads 8 comments and includes the pinned club statement. If the club's post is an announcement rather than part of the debate, it should sit above the thread as its own component and come out of the count. We assumed it is part of the discussion and can be replied to and disagreed with, which is the more honest of the two.
