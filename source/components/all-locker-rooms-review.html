What you're looking at

One list, two modes

Live and Upcoming are not two tabs of one list. The code carries a separate sort enum for each, drops one of the four scope chips in Live, and shows a different figure in the card footer — people in the room when live, people booked in when scheduled. So the segmented control at the top switches mode, and everything below it re-reads: the sort options, the filter options, the chips, the search sheet's title.

The room card is the Backchat card, unchanged — the same two-line title, the same 24 px host portrait, the same host : club_staff line, the same footer. A room has to look like the same room wherever it appears, and it now appears in seven places. The full list is not a 244 px carousel cell, so the card runs the full column width and carries the two things the peek card had no room for: the reminder control, and EDIT on a scheduled room you host.

Everything on the top half is live in this preview. Switch mode, tap the chips, open sort, tick filters and press Apply, open search and type — club_staff, arsenal, sergi_gol and goalkeeper each reach a different state. The four states below the fold (first load, loading more, end of list, the three empty panels) are laid out as specimens because you cannot get to them by tapping.

Two copy defects fixed here. The filter enum ships TO BE REMINDED ROOMS, which reads as a category of room rather than something you did; it is Rooms I've set a reminder for in this build, matching the wording already agreed in the sheets kit. And the room editor's delete dialog reads Delete this rooms? — it is Delete this room? Only one room is ever being deleted. That string lives in locker_room_editor_content_view.dart, so the fix has to be carried into the Schedule a room screen; nothing on this screen can delete a room.

Three more strings were tightened on the way through. N results found is rendered for every N in the shipped build, so a single hit reads 1 results found — pluralised here. The search sheet's title is hard-coded to Find LIVE room whichever mode you opened it from — it now follows the mode. And the filter says Closed rooms only while the card footer says Locked room for the same fact; locked wins, because that is what the padlock in the footer and the room-type tiles in the editor both say.

Pagination: there isn't any. The list view attaches a scroll listener and calls loadMoreAllLockerRooms() whenever the scroll position reaches the end and state.nextUrl is not empty — a cursor, so there are no page numbers, no page size to show and no pager to design. What that needs is exactly three things, all built above: a skeleton holding the incoming row, a marker while the request is out, and a line when the cursor comes back null.

Provenance

What is reused and what is new

Reused, unchanged

  • Room card — backchat.html, verbatim: two-line title, 24 px portrait, host : name, footer with mic count, people count and the padlock label
  • Sort and filter sheets — sheets.html: R18 top corners, grabber, 48 px rows, accent-wash selected row with a 30% rim, Clear all + accent Apply
  • Skeleton bone — states.html: white 5.5% with one 1.5 s sheen
  • Empty panels and illustrations — states.html: the "no rooms in session", "nothing scheduled" and "no search results" frames, and its rule that a state with no member action carries a promise pill rather than a button
  • Search field — forms.html control shell, 52 px, R12, accent focus ring
  • Option sets — LiveLockerRoomsSort, UpcomingLockerRoomsSort, LockerRoomsFilter, AllLockerRoomButtonType, values as shipped
  • Live / Upcoming split, and the missing chip — the code's own separation, including dropping REMINDERS in Live

New in this proposal

  • Segmented Live / Upcoming control — the code reaches this screen already set to one mode and gives no way to change it here. One control, with counts.
  • Labelled sort and filter triggers — replacing three unlabelled 32 px raster icons. The sort trigger names the applied order; the filter trigger carries the active count.
  • Multi-select filter — the code stores one filter index, so Open rooms only and Rooms I'm invited to cannot both be on. Ticks are OR within a group and AND across groups; All rooms is dropped, because "no filter" is now simply nothing ticked.
  • Radios on the sort sheet — the export draws these single-select rows with a square checkbox tick, which promises "tick as many as you like". Recorded in sheets.html and corrected the same way here.
  • Recent searches — the shipped sheet shows a blank area until you type.
  • The tally line, the end-of-list line, and the filtered-to-nothing panel
  • Stacked sheets — the filter and sort discs in the search results header open over the search sheet instead of replacing it, so the query survives
  • Date format — Sunday 19 April · 6:00 PM. Backchat's Sunday · April 19 · 6:00 PM wraps to two lines in a full-width card.
  • 44 px hit areas — every 30 px and 38 px disc takes the create-idea.html ::after expansion; labelled controls are 44 px outright

One asset defect found. In _assets/avatars.css, --av-01 and --av-17 are byte-identical, so on the Backchat home club_staff and taythaytu render the same face. In a thirteen-room list that is unreadable, so club_staff is on --av-08 here. backchat.html needs the same change.

Decisions

What we need from you

  1. Should invitations and reminders be a chip or a filter?

    They are currently both. INVITATIONS and REMINDERS are scope chips, and ROOMS I'M INVITED TO and TO BE REMINDED ROOMS are filter options — the same two facts, set from two places, on the same request. The code resolves the clash with ??, so whichever the chip sets silently wins and the filter row appears to do nothing. We have built both, as shipped so you can see the duplication. Our recommendation is to keep the chips and drop the two rows from the filter sheet, leaving filter to mean access only.

  2. Does search inherit the list's sort and filter, or start clean?

    The code keeps a second, separate sort and filter state for search and resets both to their first option every time the sheet opens — so a member who has filtered to locked rooms searches across everything without being told. We have built search inherits the list: one filter state, one sort state, and the discs in the results header open the same two sheets. If search is meant to be a fresh look at everything, the results header needs to say so.

  3. Is the filter multi-select?

    The shipped control is one index into five options, which is why All rooms has to be one of them. We have built multi-select with Apply, which is what makes the count on the trigger meaningful and lets access and involvement combine. It is an API change as well as a UI one: the endpoint currently takes a single type.

  4. Should search debounce?

    The shipped field fires a request on every keystroke with no debounce, so typing eight characters costs eight requests and the results flicker between them. We assume 250 ms and a minimum of two characters. Confirm, and confirm whether search should also cover past rooms — today it only reads the mode you opened it from.

  5. Do we keep two names for one thing?

    A room is Closed in the filter enum and Locked on the card, the editor tiles and the padlock. We have standardised on locked and would change the enum label to match. Same question for the person on the card: the byline renders a username (host : club_staff) while other screens show a display name.
