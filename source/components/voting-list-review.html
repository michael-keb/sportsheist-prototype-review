What you're looking at

The rail shows four ballots; this is all of them

An Idea that collects enough Likes becomes a Proposal, and Barcelona votes on it. This screen is every Proposal currently in that stage, at full column width, with the controls the rail had no room for: a Decisions / Positions switch, a category chip row that changes with the switch, a sort sheet, a filter sheet and search.

The card is untouched. It is voting-card.html's card — the same 8px threshold bar with its 14px knob and its threshold tick, the same now / required figure pair, the same verdict pill and the same 52px outlined CTA — with one edit: it runs the full column instead of a 268px rail cell.

Three findings from the code shape this screen. There is no pagination and no infinite scroll — one request, limit: 50, next ignored. The sheet the filter glyph opens only sorts. And getListVotingNoLimit re-sorts the page ascending by vote count after the request, so the list arrives least-supported first while the sheet says MOST RECENT is applied.

New in this proposal

  • Search — no proposal search endpoint exists; built as a client-side match on title and author over the loaded page
  • The filter sheet — the app has none. Every option is an existing field: status, type, isVote, isDanger, and voted compared against findTargetVote()
  • The applied sort, shown on the trigger
  • Sorting the list to match its own label — the shipped screen sorts ascending by vote count after the request and never says so
  • The tally line and the end-of-list line
  • The cap notice — limit: 50 is a real ceiling
  • The empty state — the shipped screen has none, and no pull-to-refresh either
  • Pull-to-refresh — voting_screen.dart has no RefreshIndicator at all, unlike ideas_screen.dart
  • The filled CTA on an unvoted ballot — the shipped card gives every state the same text link, so a ballot needing a vote looks like one already cast
  • The hold hatch on the threshold panel — voting-card.html carries the held state as a neutral bar and a pill; the hatch is added so held reads as held at a glance, per the contract
  • The FINAL word on a red clock
  • Dropping the tooltip discs — the segment's two question-mark discs are wired to lorem ipsum

Decisions

What we need from you

  1. Should this list paginate at all?

    It does not today. getListIdea sends limit: 50 with no offset and no cursor, and next is never read. We have assumed 50 is a real cap and the screen should say so. If a club can exceed 50 live ballots this needs cursor paging or server-side chip filtering.

  2. Which order should the list actually arrive in?

    getListVotingNoLimit requests ordering=recent and then runs dataListActive.sort((a, b) => a.voted.compareTo(b.voted)) — ascending, so the least supported Proposal is first while the sheet reports MOST RECENT. We have assumed the label is right and the extra sort is a bug. If putting the ballots that need help first is deliberate, it should be a fourth sort option with a name, not a silent override.

  3. Should Voting have pull-to-refresh?

    ideas_screen.dart wraps its body in a RefreshIndicator; voting_screen.dart does not. Since counts move second by second and the screen is driven by a socket stream, a member who suspects a stale figure has nothing to pull. We have assumed it should be added, matching Ideas.

  4. Is the sheet a sort sheet or a filter sheet?

    The file is widget/show_filter.dart, the trigger draws a filter glyph, and everything inside sorts. We have assumed two sheets — Sort with the code's three real options, and a new Filter sheet, because sort applies instantly and filters need an Apply.

  5. Should closed Proposals stay in this list?

    getListVotingNoLimit keeps only active and veto statuses, but getFilterListIdea — the call every chip and sort tap uses — does not apply that filter, so a settled Proposal can appear the moment a member touches a chip. We have assumed closed ballots belong here, with their own filter tick and a View result CTA, and that the two calls should agree. The alternative is excluding them from both and sending members to Results.

  6. Do the chips need to match Ideas?

    Voting offers five chips under Decisions; Ideas offers two. That is what the code does, and we have kept it — but the same Proposal passes through both screens, so a member can filter to MANAGEMENT while voting and not while liking.

  7. Is “Support” one figure or two?

    The shipped card draws a two-ended bar labelled Reject and Approve, then prints a single N% Support figure beneath it. Two readings of the same number in one panel. voting-card.html resolved this as one figure against a threshold and we have kept that, but if a ballot genuinely has more than two options the panel needs the ranked list instead.
