What you're looking at

The rail shows three ideas; this is all of them

The War Room's Ideas rail is a carousel: it peeks three cards and then stops. This screen is the same cards, run at full column width, with the controls the carousel had no room for — a Decisions / Positions switch, a category chip row, a sort sheet, a filter sheet and search.

The card itself is untouched. It is idea-card.html's card — the same 16px padding, 17px title, 64px gauge ring, tabular clock and 52px Like pill — with one edit: it runs the full column instead of a 268px rail cell. A list is not a licence to redesign the card.

Two things about the shipped screen are worth saying plainly before the anatomy. There is no pagination and no infinite scroll: one request, limit: 50, the response's next ignored. And the sheet the toolbar's filter glyph opens only sorts — its three options are the whole of it. Both are documented below rather than designed around.

Provenance

What is reused and what is new

Reused from the library and the code

  • The Idea card — idea-card.html, unchanged but for width:100%
  • Sheet shell, option row, checkbox and radio — sheets.html
  • Search and text controls — forms.html's 52px field
  • The skeleton bone — states.html
  • The hold hatch — veto.html, via the contract
  • The screen furniture — back disc, eyebrow, 34px title, segment, chips, tally and end-of-list line all come from all-locker-rooms.html, the sibling "view all"
  • Segment labels — CLString.listFilterPri, in enum order
  • Chip labels — CLString.listFilterSupIDea, index 0 dropped
  • Sort options — CLString.listSortProposal, all three, in order
  • Card-state branches — ideas_screen.dart's own pending / veto / rejectVeto / isDanger splits
  • CTA wording — ideas_screen.dart's actions.like / actions.view strings
  • The create entry point — CRoute.warningIdea, gated on CIdeaPost.canPost, landing on idea-gate.html

New in this proposal

  • Search — there is no proposal search endpoint; getListIdea takes no query parameter. Built as a client-side match on title and author over the page already in memory, so it ships with no backend work
  • The filter sheet — the app has none. Every option is an existing MProposal field: status, type, isVote, isDanger
  • The applied sort, shown on the trigger — the shipped trigger is a bare glyph, so the order is invisible until the sheet is opened
  • The tally line — the count of what is currently showing
  • The end-of-list line — the shipped list simply stops
  • The cap notice — limit: 50 is a real ceiling and nothing in the app admits it
  • The empty state — the shipped screen has none at all
  • The filtered-to-nothing panel — distinct from a genuinely empty stage
  • The FINAL word on a red clock — the shipped card carries the state in the plate colour alone
  • Dropping the tooltip discs — the segment's two 16px question-mark discs are wired to tooltips whose body is Lorem ipsum dolor sit amet. Not rebuilt until there is copy

Decisions

What we need from you

  1. Should this list paginate at all?

    It does not today. getListIdea sends limit: 50 with no offset and no cursor, and the response's next is never read — so the 51st open Idea is unreachable. We have assumed 50 is a real cap and the screen should say so rather than silently truncating. If a busy club can exceed 50 open Ideas, this needs either cursor paging (the pattern all-locker-rooms.html already documents) or server-side filtering on the chips.

  2. Is the sheet a sort sheet or a filter sheet?

    The file is show_filter.dart, the trigger draws a filter glyph, and everything inside sorts. We have assumed two separate sheets — Sort with the code's three real options, and a new Filter sheet. The alternative is one combined sheet, but sort is single-select and applies instantly while filters are multi-select and need an Apply, so combining them mixes two commit models in one surface.

  3. What do the tooltips on Decisions and Positions say?

    Both halves of the segment carry a question-mark disc wired to a tooltip whose body is currently lorem ipsum. The distinction between a Decision and a Position is the single most load-bearing idea on this screen, so it needs real copy. We have removed the discs until it exists.

  4. Should the chip row for Ideas match Voting's?

    Voting offers five chips under Decisions — ALL, ON-FIELD, OFF-FIELD, MANAGEMENT, MY IDEAS. Ideas offers two: ALL and MY IDEAS. That is what the code does (listFilterSupIDea versus listFilterSup) and we have kept it, but the same Idea passes through both screens, so a member who filters to ON-FIELD while voting cannot do it while liking.

  5. Is pull-to-refresh meant to jump to the bottom?

    _reloadPage() calls scrollController.jumpTo(position.maxScrollExtent) before re-fetching, so pulling down from the top throws the member to the end of the list. We have assumed this is a bug and refresh should stay where it is.

  6. Does a scheduled Idea belong in this list?

    It appears here today, but it is the member's own draft, visible to nobody else, with no clock and no Like. It reads as a different object in a list of live ones. We have kept it in place and given it a filter tick of its own, but moving drafts to the profile is defensible.
