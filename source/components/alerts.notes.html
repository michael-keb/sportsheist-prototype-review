The fourth of the five navigation tabs. It is the one place a member is told that something they have a stake in has moved — a vote closing, an Idea promoted, a veto upheld, Merits awarded — and it is the screen the notification badge points at. Four screens: the feed, and the three states it passes through before it gets there.

What you're looking at

A designed screen for an undesigned tab

Alerts has a tab, an icon and a badge in every frame of the Figma file, but no screen behind it. The live build has one — alert_body.dart renders a flat list of rows and marks them read on tap — so unlike Merits or Profile there is real behaviour to respect here, just no visual design for it.

This is a rebuild of that list in the dark-mode language. The two changes of substance are that alerts are grouped by day rather than run as one undifferentiated stream, and that an alert which is asking for an action now carries that action on the row. Everything else — the hero, the bordered section, the accent-wash row treatment — is lifted from screens already signed off.

Ten alerts are shown across four day groups, four of them unread. Eight of them are alert types the shipped build already raises; two are proposals. The whole thing is live: tapping a row marks it read, the 4 unread pill and each group's 3 new counter recount, and Mark all read disables itself when the feed is clear.

Why four phones. The empty state used to sit under the live feed on the same scroll, which showed it but did not show what it replaces. It is now its own frame, with loading and load-failed beside it. The last of those is the finding worth stopping on: the build does branch on failure, and it renders No message added yet — the same widget and the same string as an empty inbox. A member whose request died is told they have no alerts. Frame 04 separates the two, and gives the retry a visible control instead of a pull gesture nobody is told about.

Provenance

What is reused and what is new

Nothing on this screen was designed in Figma. The tab exists in every frame; the screen behind it does not. Every pattern below was taken from a frame that was designed, and assembled into a layout that was not.

Reused from the Figma file

  • Hero banner — field gradient, triangle motif, acid peaks, prop-in-front layering
  • Section container — the Locker Rooms bordered wrapper and its 1 px hairline
  • Status pill — the LIVE NOW treatment, reused for the unread count
  • Icon button — the 38 px circle from the War Room section headers
  • Row — padding and hairline top border from the data rows in the exports
  • Unread treatment — the accent wash and 3 px edge marker built for the viewer's own row in Merits
  • Tab bar — reconstructed from the four active-state frames
  • Photography — both portraits lifted from the same exports
  • Alert content — eight of the ten rows are shipped alert types from popup_type.dart, rewritten as sentences

New in this proposal

  • The whole screen — layout, hierarchy and reading order
  • Grouping by day — the live build renders one flat list with no dividers
  • Day header — day, date and per-day new count
  • Glyph vocabulary — eight drawn icons, one per alert type, so a type is recognisable before it is read
  • Inline action pill — Open room, Vote here, View details; the build has no per-row action at all
  • Emphasis rendering — the server's **bold** runs promoted to white weight 600
  • Unread system — the four-signal marking, the live counters and Mark all read
  • Empty state — no empty frame exists for this tab, and the shipped string is a hardcoded No message added yet
  • Dark skeleton — the shipped shimmer is Colors.grey.shade300 → shade100, a light-theme skeleton on a dark screen. Its structure is kept; its palette is not
  • Load-failed screen — the branch exists in code but spends itself on the empty-inbox box. The mark, both sentences and the retry are new
  • Two alert strings — the locker-room reminder and the vote-closing warning have no matching type in the shipped list; both are proposals
  • Search — the magnifier opens a real field that filters every day group in the feed
  • Settings entry point — placed, not designed; the destination is Account settings

The magnifier is live. It was an aria-hidden glyph on a button with no handler; it now opens a field that filters the feed on every word in an alert — title, body and the emphasised names inside it. A day group whose alerts have all been filtered out hides its heading with them rather than leaving an empty Yesterday behind, and a search that matches nothing says so. Esc closes the field, clears it and returns focus to the glyph. Search is deliberately independent of the unread system: the unread pill and the per-day N new counts keep counting the whole inbox, because how many alerts you have not read is not a function of what you happen to be searching for.

Decisions

What we need from you

  1. What is the spendable currency called?

    This one screen has to name it three times and there is no agreed name. The build uses Credits, Participation Credits, Participation Deposit and a legacy BOND; the API returns Reputation Points; the new navigation says Merits. The rows here read Merits for what you earn and Participation Deposit for what you stake, because they behave differently — but if they are one balance they need one word, and if they are two things the difference needs explaining somewhere a member will see it.

  2. Should tapping an alert go anywhere?

    The shipped row only marks itself read, which is why the action lives on an explicit pill here. That is defensible but unusual: most people expect a notification to be a link. We have assumed tap marks read, the pill navigates. If the whole row should navigate, the pill becomes redundant and the alerts with no destination need a different treatment.

  3. Do reminder alerts exist?

    Two rows — Manager Auto Room starts in 15 min and Voting closes in 2 hr — are alerts about something that has not happened yet. Nothing in the shipped type list raises them, and they are the two most useful alerts on the screen. Confirm they are wanted and we will specify the trigger windows.

  4. Is there a settings screen behind that button?

    The control bar and the empty state both offer Alert settings, on the assumption that a member can mute categories. Nothing like it exists in the build or the Figma. If per-category muting is out of scope, both entry points should be removed rather than left pointing nowhere.

  5. Should a failed load say so?

    Today it does not. ActionStatus.fails is checked, and it draws No message added yet — byte for byte the empty-inbox box. So the two states a member most needs to tell apart are the same picture, and the only way back is a pull-to-refresh that nothing on screen mentions. We have drawn a distinct failure panel with a visible retry. Confirm the words: both sentences are ours, because the shipped string is an English literal rather than a translated one and is not reusable. While that is being decided, the empty string itself is worth a look — message is not a word this product uses anywhere else.

  6. Does this feed also drive push?

    Grouping by day and a per-day new count only make sense if a member can come back to a backlog. If every alert also fires a push notification the in-app list becomes a receipt rather than an inbox, which argues for a shorter retention window and a different empty state.
