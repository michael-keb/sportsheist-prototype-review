The full-screen photo viewer and the swipeable gallery — the surface members land on when they tap any photo in a locker room, a chat, an idea or a profile. Both surfaces exist in the shipped app and neither has ever been designed, specified or screenshotted.

What you're looking at

Two screens nobody has seen yet

Every photo in SportsHeist is tappable, and tapping one pushes a brand-new full-screen route. There are two of them: one for a single photo, one for a set of photos you can swipe through. Neither appears anywhere in the specification set, in the Figma file, or in the component library — they were built once, early, and never reviewed. This is the first time they have been drawn.

What ships today is a purple app bar sitting on a grey field, with a plain white text link reading Tải xuống in the corner, an index counter tucked behind the notch, and no loading state and no failure state at all. If a photo is slow, you get nothing; if it never arrives, you get nothing forever. There is a caption editor hidden in there too, on a grey button, in Vietnamese.

The nine screens here rebuild both surfaces on the same sheet, dialog and button shells the rest of the library already uses, and add the four states the code is missing: loading, failed, saving, and saved. Frame 09 answers the one genuine design question the viewer raises — what colour a photograph should sit on.

Provenance

What is reused and what is new

Reused, unchanged

  • Sheet shell — sheets.html: 18 px top radius, 40 × 4 grabber, tracked-caps title, 54 px action rows, full-width ghost Cancel, drag-to-dismiss past 90 px
  • Dialog shell — dialogs.html: R16, 20 px padding, 44 px icon tile, 46 px action pair, verb repeated on the affirmative
  • Toast — dialogs.html: inset, R16, 3 px semantic leading mark
  • Skeleton — states.html: rgba(255,255,255,.055) bone, one 1.35 s sheen
  • Ring spinner — states.html: 90° accent arc on a white-18% track, 0.9 s, stroke thickening as the ring shrinks
  • Textarea — forms.html: R12 on --sunken, accent focus ring, 16 px input
  • Tap-target expansion — create-idea.html's ::after pattern, keeping the sampled 38 px disc while meeting 44 px
  • Photography — the portrait set from _assets/avatars.css, on the same username-to-face mapping as the rest of the library
  • Index counter as a concept — image_widget.dart:225, '${index}/${length}'
  • Pinch to zoom — InteractiveViewer(maxScale: 5.0), and drag-down-to-dismiss, both already in the code
  • Caption editing — UDialog().showForm at image_widget.dart:255, a real feature nobody has documented

New in this proposal

  • Pure-black viewer ground — declared as --photo: #000000 and scoped to the viewer only. It is the one place in the system that is not --bg. See Ground, frame 09
  • A loading state — the code has none; the viewer pushes with the network request un-started
  • A failed-to-load state — the code has none. Today a dead URL is a permanently empty screen
  • Save-and-share sheet — replaces the bare white text link Tải xuống, which has no hit target of its own and no confirmation
  • Determinate save progress — the code shows an indefinite snackbar with no byte count and no way to stop
  • A save-refused state — the code checks check['isSuccess'] and, if it is false, shows nothing at all
  • Page dots — the PageController position made visible, and tappable
  • A close control — the shipped leading control is a 105 × 40 row reading ‹ Quay lại. Untranslated, and “back” is the wrong verb: a viewer is dismissed
  • Attribution in the bar — the shipped app bar title is the empty string
  • English throughout — Tải xuống, Chú thích, Thêm chú thích cho ảnh, Đang tải ảnh về... and Tải ảnh về thư viện thành công are all shipped Vietnamese strings in this one file
  • Report a photo — no moderation path exists on any photo surface today

Decisions

What we need from you

  1. Is pure black right for a photo viewer, given the canvas is #030401?

    Our ruling: yes, and it is the only exception in the system. Three reasons. One, #030401 is a colour with a green cast — G is higher than R and B — so under a photograph it tints the letterbox and draws a faint frame the photograph did not ask for. Two, black is absence: on OLED the bars switch off, so a dark photo has no edge at all, which is exactly what iOS Photos and every other viewer does. Three, the cost is nothing measurable — black against #030401 is 1.02:1, invisible, so the cut from app canvas to viewer ground cannot be seen even when you look for it. Frame 09 puts the same photograph on all three candidates so the difference can be judged rather than argued.

    The premise needs one correction, though: the live viewer is not on black. backgroundColor: CColor.black resolves to that MaterialColor's primary value, 0xFF2C2C2C. The shipped ground is a mid grey measuring 1.50:1 against black — clearly visible, and it flattens every dark photograph in the app. Whichever way this decision goes, #2C2C2C is wrong and has to change.

  2. Should saving a photo be one tap or two?

    Today it is one: Tải xuống writes straight to the camera roll. We put a sheet in the way, because the same control now carries Share, Copy link, Edit caption and Report, and because a single mistap writing to somebody's photo library is not recoverable from inside the app. If you would rather keep one-tap save, we would add a Save disc beside the sheet disc rather than remove the sheet.

  3. Dots or a thumbnail rail past ten photos?

    Dots stop working somewhere around ten — they either shrink below a usable target or run off the screen. We have assumed dots to ten, a scrolling thumbnail rail beyond. The counter pill stays in both cases, so the number is never lost. We need to know the real maximum: WUpload's maxCount is per-field and nothing caps a locker-room gallery.

  4. Who can edit a caption, and can it be removed?

    onChangedDescription is passed only from the upload field, so in practice captions are editable while you are composing and frozen afterwards — but nothing in the code says so. We have built it as the poster can edit their own caption at any time, and emptying the field removes it. If captions should freeze once the room opens, the pill needs to disappear at that moment rather than fail on submit.

  5. We need one real photograph.

    _assets contains no full-size imagery. The only photography in the kit is the sixteen portraits in avatars.css at 112 × 112, so every plate on this page is one of those upscaled and is visibly soft. The geometry is right; the render is not. One 1080-wide match-day photograph — ideally one portrait and one landscape — would let us show these frames properly. We have not drawn a substitute, because a fake photograph is worse than a soft real one.

  6. Is a report path in scope?

    There is no moderation route on any photo surface in the app. We have put Report this photo in the sheet because a member-photo surface without one is a liability, but it needs somewhere to go. If there is no moderation queue yet, say so and we will pull the row rather than ship a dead end.
