Every surface that puts a photo into SportsHeist — the profile-picture picker, the match-photo field, the upload confirmation, and the multi-select list that shares the same shell. Three of these sheets exist in the shipped app and are captured nowhere: the coverage audit lists the avatar picker as “Not captured” and the multi-select sheet as unused.

What you're looking at

The sheet behind every plus button

One widget, WUpload, handles every image upload in the app: your profile picture, locker-room photos, idea attachments. Tapping its plus button opens a bottom sheet offering three ways to get a photo in. That sheet has never been screenshotted, specified or designed — it is a bare list in an eight-pixel margin, with no title, no grabber, no rounded top and no safe-area inset, so its last row finishes inside the home-indicator gesture zone.

More importantly, it validates nothing. No size limit, no format check, no compression, no cropping. A member can pick a 40 megapixel HEIC straight off a new iPhone and the app will stream the original bytes at full size to the server. If the upload fails, it fails silently: the file simply is not there, with no error, no toast and no retry. There is no progress either — one indefinite Vietnamese snackbar covers the whole batch, with no count, no percentage and no way to stop.

The nine screens here rebuild the source sheet, the confirmation and the multi-select list on the library's existing sheet and dialog shells, and add the five states the code is missing: a permission prompt, real per-file progress, a failure you can retry, a rejection that explains itself, and a result. Every screen is marked below as either real — it exists in upload.dart — or proposed.

Provenance

What is reused and what is new

Real — it exists in the code today

  • The source sheet itself — upload.dart:378, showModalBottomSheet. AU-10:102: “Avatar picker sheet — Not captured”
  • Three sources, and only three — gallery single, gallery multiple, camera. Two video rows exist but are commented out at upload.dart:414–427, and the isVideo branch that would use them is commented out at :250, so video cannot be picked
  • The confirm dialog — upload.dart:276, showDialog → a bare AlertDialog holding a GridView of the picked files
  • The multi-select sheet — select_multiple.dart:84. AU-09 records it as not used on that screen; it is captured nowhere
  • Four-across grid — upload.dart:110
  • Count in the label — upload.dart:84
  • A count cap — maxCount, checked at :220 for the Add tile and at :348 during upload
  • Remove with confirmation — upload.dart:167, UDialog().showConfirm
  • Selection count in the trigger — select_multiple.dart:191, 'Đã chọn: n'
  • Search inside the sheet — select_multiple.dart:105, debounced by Delay()
  • Selected-row highlight — select_multiple.dart:144, CColor.primary.shade100

Proposed — it does not exist today

  • Any validation at all. No size check, no format check, no dimension check, no compression, no cropper. pickImage() is called with no maxWidth, no maxHeight and no imageQuality (upload.dart:261); postUploadPhysicalBlob (api.dart:237) reads the file's length only to build the multipart part, never to test it. pubspec.yaml has no flutter_image_compress and no image_cropper
  • The 7.5 MB and JPG / PNG / PDF limits. These belong to the GBG vendor web view (CA-15), which is a third-party page inside a web view, not to upload.dart. They are quoted here as the most defensible starting numbers, not as a capture
  • Any upload progress. The listener at upload.dart:102 shows one indefinite snackbar for the whole batch. No bytes, no count, no percentage, no cancel
  • Any failure feedback. A failed upload returns null and is skipped at :359. No error, no toast, no retry — the file is simply absent
  • A permission pre-prompt. image_picker raises the OS prompt implicitly. There is no in-app explanation, no denied state and no route to Settings. permission_handler is in pubspec but is used only for Android storage in downloadFile
  • A sheet shell. The shipped sheet is a bare Wrap in an 8 px horizontal padding: no title, no grabber, no top radius, no safe-area inset
  • Remove in the sheet — the avatar's 96 px disc has no remove badge, so today there is no way to clear a profile picture from that screen
  • The supplied-portrait rail — carried over from onboarding.html; not in upload.dart
  • Sizes, times and Undo on the result
  • English throughout. Đang tải ảnh lên..., Xóa ảnh đã chọn, Bạn có chắc muốn xóa ảnh hiện tại không?, Đã chọn: n, Thông báo! and Vui lòng chọn tối thiếu 1 lựa chọn are all shipped strings in these two files
  • Dropping #E04A09 — the remove badge's orange is a third hue. Destructive is #E2564A

Decisions

What we need from you

  1. What is the real size ceiling, and which formats does the endpoint accept?

    This is the one thing we cannot invent, and the one thing that will produce support tickets on day one. upload.dart enforces nothing, so today the answer is “whatever the server does”, discovered by the member as a silent failure. We have built to 7.5 MB and JPG / PNG because those are the numbers the GBG identity page already shows members — but that is a different vendor on a different endpoint, and PDF makes no sense for a match photo. We need the upload endpoint's actual limits.

    Related and just as important: should the app compress before uploading? A current iPhone photo is 3–6 MB and a burst of six is 30 MB on a stadium 4G connection. We would resize the long edge to 2048 px at 85% JPEG client-side, which puts almost every photo comfortably under any ceiling and makes the rejection screen rare rather than routine. That needs a decision because it is a code change, not a design one.

  2. Should HEIC be accepted or converted?

    Every iPhone shoots HEIC by default, so “send JPG or PNG” is a rejection most iPhone members would hit. We have shown HEIC as a rejection in frame 07 to make the state legible, but converting HEIC to JPEG on device is almost certainly the right answer and removes the whole screen. Same decision as compression, same code change.

  3. Should a single photo be confirmed, like a batch is?

    Today it is not: showConfirmImage is reached only from the multi-pick branch, so choosing one photo from the library, or taking one with the camera, uploads it immediately with no preview and no chance to back out. We have assumed confirm every upload, batch or single, on the grounds that a photo of the wrong person going into a locker room is not recoverable by the member. If you would rather keep single picks instant, the sheet row should say so.

  4. Is the profile picture cropped, and by whom?

    There is no cropper anywhere in the path, so a landscape photo becomes a circle by BoxFit.cover centred on the middle of the frame — which cuts heads off. We have assumed a square crop step with a draggable frame before upload, but we have not drawn it, because it is a screen in its own right and it depends on the compression decision above. Flag it if you want it in this pass.

  5. Should the multi-select sheet be revived, or removed?

    WSelectMultiple is fully built and, per AU-09, is used nowhere. We have drawn it as Sports you follow because that is the most plausible real use and it is the field the onboarding flow arguably needs. But a component with no caller is dead code, and dead code with a designed appearance invites someone to wire it up in the wrong place. Either name the screen it belongs on, or we mark it deprecated and drop it from the library.

  6. Can the maximum photo count be stated on screen?

    maxCount is optional. When it is null the label shows no count and the Add tile never disappears, so there is no ceiling a member can see. We have assumed every upload field declares a maximum and shows it, because a field that silently stops accepting photos is indistinguishable from a broken one. That means naming a number for each surface — locker-room photos, idea attachments, profile.
