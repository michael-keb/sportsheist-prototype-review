Profile is tab 5 of 5 — the account hub. It answers four questions: who you are, which club you play for, what you hold, and where every setting that belongs to you lives. Five screens: the two states the capture set documents, plus loading, load-failed and a guest reading.

Since this was written — 31 July 2026

Four of the defects below have been fixed in the app

These notes argue from the code as it stood when the screens were drawn. Some of that code has since changed, because these findings were acted on. The screens are still the right proposal — but do not read the following as outstanding faults.

  • A failed profile load no longer shimmers forever. profile_body.dart now has a buildErrorState() with a message and a Try again button wired to loadProfile. Frames 03 and 04 proposed exactly this; the app has it. Frame 04 is now that screen, rebuilt with the app's own copy — so this is the one item below that has moved from a gap to a rebrand.
  • The leader-status bands now meet. The three tests are >= 0.95, >= 0.85 and >= 0.75, so a member sitting exactly on a boundary no longer falls through to MEMBER.
  • The dead menu rows are gone. The switch with its bare case 0: break; has been replaced by a profileRows list, so the menu can no longer render a row with nothing behind it.
  • Having no club is no longer treated as a failure. The default-club lookup used to throw when it returned -1; it now falls back to the first club, and leaves the current club null when there are none. That is what lets frame 04 mean a real failure and frame 05 mean an account with no club — two readings that used to arrive at the same screen.

Everything else in this file was re-checked against the code on the same date and still holds.

What you're looking at

Identity, club, credits, settings

The current build opens Profile with a black slab, a centred name in a display face and a third-party club crest sitting loose on the canvas. This proposal keeps all of the same content and routes, and rebuilds it on the dark-mode language: the PROFILE banner is the same construction as the Merits banner, the identity block is a card, and the seven navigation rows become four labelled groups.

Why five phones. The capture set documents Profile as two screens — PR-01 at scroll 0 and PR-02 the same route scrolled about 330pt to the menu list. They are one route, but they are two documented states, so each gets its own frame here rather than being stacked in one scroll. Frames 03, 04 and 05 are states no capture shows: what the screen looks like while it is loading, what it says when the load fails, and what it looks like for someone who has not joined a club yet.

The club affiliation is the piece that needed a real decision. Crests are artwork we do not own and cannot restyle — on the shipped club card a yellow crest measures about 15:1 against the surface while a blue one drops to about 1.4:1 and dissolves. Every crest on this screen therefore sits on the app's own plate, and we measure the plate rather than the crest. That number is then identical for every club in the catalogue.

The settings list carries one rule that the current build does not: a row with a chevron goes somewhere, a row without one never does. That is what tells an editable field apart from a read-only one — today all eight account fields look identical although only three accept input, and two rows that navigate nowhere at all look exactly like the five that do.

Provenance

What is reused and what is new

Reused from the Figma file

  • Token block — copied verbatim from Merits, which sampled it from the War Room and Backchat dark-mode exports.
  • Hero banner — same gradient, field triangles, acid peaks and knockout athlete as the Merits banner.
  • Section container and section header — the bordered Backchat wrapper holding a status pill, and the Merits label-plus-pill header.
  • Status pill, card, row, tab bar, avatar — the established patterns, unchanged.
  • Crest plate — the canonical light plate settled in Club selection: three sizes only, 28 / 40 / 64px.
  • Confirm dialog — the canonical dialog shell, red icon tile and ghost/danger action pair from the Dialogs kit.
  • Read-only field — the muted value plus padlock idiom from Account settings.
  • Skeleton bone — the States kit's bone and single sheen, as used in Ideas list.
  • Portrait — --av-08, the same face Merits uses for the signed-in user.

New in this proposal

  • Identity card — avatar, name, handle, tier and club in one --surface card, replacing the black slab, the centred display-face name and the violet glow rule.
  • One photo-edit control — a 26px button on the avatar, replacing the UPDATE text link that currently has an empty handler. It opens a working photo sheet: pick a portrait and the avatar on that frame changes, or remove the photo and it falls back to the no-photo placeholder.
  • Compact identity strip — frames 02 and 03 open below the banner, so they carry a 36px avatar, name and tier instead. It replaces the fixed black header panel that content currently disappears behind.
  • Stat strip — Merits total and season rank as two --sunken panels; the current build shows 2545 REPUTATION POINTS as a centred line.
  • Club section — the current club as a lockup on a plate, the other registered clubs beneath it, and a Clubs ↗ header pill. The current build shows one crest, uncontained, and puts the club behind a CURRENT TEAM row.
  • Credits card — available dominant, locked recessed in a panel, replacing the two-equal-halves split card.
  • Grouped settings at one height — four labelled groups at 56px, replacing seven ungrouped 72pt cards.
  • Chevron rule — chevron means it navigates; padlock means it cannot change. The new part is that the two now look different.
  • Destructive log out — its own group, semantic red, and a confirmation step that does not exist today.
  • Count badge — 6 in a pill rather than concatenated into the label.
  • Loading frame — a dark skeleton covering the whole body, replacing a light-theme grey shimmer on a dark screen.
  • Load-failed frame — new drawing only. The state itself now exists in the app and both sentences are its own strings; what is new is the panel, the red icon tile, the accent retry with --acid-ink in place of white on #E70A0A, and the in-button spinner.
  • Guest reading — a whole screen the shipped code cannot produce: quiet standing pill, no-photo avatar, explained empty club state, zeroed figures.
  • Unavailable row — a row that says why it cannot be used instead of looking identical to a live one.
  • Notifications and Security on Profile — both sit one level down, inside Account settings, in the current build. Surfacing them here is a flattening proposal, not a transcription.
  • 44px hit areas — the invisible ::after expansion on every sub-44 control (tab, header pill, photo edit, dialog close), keeping the sampled visual size.

Decisions

What we need from you

  1. Should a failed load tell apart no connection from a server fault?

    This was the most urgent question on the page and the app has answered it: a failure now shows a message and a retry, and frame 04 is that screen, built with the app's own words. What is left is that there is only one of it. The detail line reads Check your connection and try again, which is the right sentence when the phone is offline and the wrong one when the server returned an error the member cannot do anything about. The States kit draws these as two panels — You're offline and Request failed — and we have drawn the single combined one here, because the app has no connectivity handling anywhere to branch on. If the offline case is worth telling apart, it needs a connectivity check first; otherwise this one panel is the honest answer and the copy should stop naming the connection.

  2. Who is a guest, and what may they do?

    The tier function returns a guest value, but it decides by comparing the user's role code against a translated display string, so it only ever fires if the API's role code is literally the English word guest — the one value the translation file happens to hold in lower case. Standing is decided by a string comparison against copy, which will break the first time that copy is edited. We drew a guest who can hold credits, buy credits and manage child accounts, but whose Hall of Fame and Achievements rows are unavailable until they join a club. Confirm the role code and the permissions.

  3. Where does a user join a club?

    There is no add-club form in the app — the flow ends on a message telling the user to log in on desktop. We drew an empty state that says registration happens on the website, with no button, because a button that opens a browser is a decision we cannot make for you. Same question applies to child accounts, which are also web-only.

  4. Do Hall of Fame and Achievements ship in this release?

    They are not in the same position. Achievements has a screen and a registered route; only the navigation call is commented out, so it is a one-line fix. Hall of Fame has no screen, no route and an empty handler — there is nothing behind it anywhere in the snapshot. We drew both as ordinary live destinations on frame 02. If Hall of Fame is not ready, it needs the unavailable treatment shown on frame 05.

  5. Are membership tiers a ladder the user should see?

    The code returns one of MEMBER, EARLY INFLUENCER, EMERGING INFLUENCER or LEADING INFLUENCER from a points ratio, but no thresholds are documented and the bands do not quite meet — a user sitting exactly on 0.75, 0.85 or 0.95 falls through every branch and reads as MEMBER. We drew a plain Member pill with no progress and no next-tier hint. If the ladder is a product feature, this pill becomes a progress component and the thresholds need writing down.

  6. What locks a credit, and when does it release?

    Nothing in the build explains Locked — no tooltip, no link, no copy. We drew a labelled figure with a padlock and no explanation. One sentence from you turns it into something a user can act on.

  7. Can support change a locked field, and how does the user ask?

    Several account fields are read-only in code. We drew a padlock with no route out. If support can edit them, the row needs a destination; if nobody can, the padlock should say so.

  8. Should Notifications and Security sit on Profile or inside Account settings?

    In the build they are inside Account settings, and Security's navigation call is commented out there. We drew both on Profile, in the Account group, on the grounds that burying notification settings two levels down is why nobody finds them. Say the word and they go back one level.

  9. Should Profile repeat the season rank?

    Rank 12 and the merits total both belong to tab 2. We drew both, as a summary that links there, because the current screen already shows reputation points on Profile. Say the word and the strip drops to Merits only.

  10. Is a three-club account the normal case?

    The clubs list shows Barcelona, Dortmund and Man United for this user, and a three-club limit is referenced but not implemented. We drew one current club and two registrations, with no limit stated.

  11. Does tab 5 need its own hero prop?

    Profile reuses the Merits athlete, the only knockout prop in the asset set. Reviewed side by side the deck repeats it. If Profile should carry a different figure, we need one cut-out — we will not draw a stand-in.

  12. Which name and which numbers are real?

    The account values match the Account settings screen so the deck shows one person; the credit balances are the build's seed data (600,611.5 and 250.0). Confirm the currency name participation credits and whether reputation points are now Merits everywhere.
